# Azure Data Architecture

> Initial architecture (v1) — this document describes the team's working baseline. It is expected to evolve as the homologation logic, data volume, and workflows mature.

## Overview

The project uses **Azure Data Lake Storage Gen2 (ADLS Gen2)** as the cloud storage layer for the financial data pipeline.

The storage account uses **Hierarchical Namespace (HNS)** so that the data can be organized in a directory-based structure and accessed programmatically from Python.

The project follows a zone-based architecture:

```text
Azure Storage Account (ADLS Gen2)
│
├── raw/
├── interim/
├── processed/
├── reference/
└── panel/
```

The architecture separates the original source data from extracted files, transformed datasets, homologation reference material, and the final analytical panel.

---

## 1. Raw

`raw/` contains the original files obtained from the source.

For this project, the original SCVS ZIP files are stored here without modification:

```text
raw/
├── estadosFinancieros_2021.zip
├── estadosFinancieros_2022.zip
├── estadosFinancieros_2023.zip
├── estadosFinancieros_2024.zip
└── estadosFinancieros_2025.zip
```

### Rules

- Original files are preserved exactly as received.
- Files in this zone are not manually modified.
- Source filenames are preserved.
- `raw/` acts as the immutable source layer of the pipeline.

---

## 2. Interim

`interim/` contains files obtained after extracting or preparing the original source packages.

The source structure is organized by year:

```text
interim/
└── financial_statements/
    ├── 2021/
    ├── 2022/
    ├── 2023/
    ├── 2024/
    └── 2025/
```

This zone is intended for extracted source files and intermediate artifacts that are necessary before the homologation and transformation stages.

The objective is to preserve the relationship between the original files in `raw/` and the data that will be processed by Python.

---

## 3. Processed

`processed/` will contain datasets generated by the Python processing pipeline.

The first processing stage is the account homologation required to make the different financial structures comparable across years, using the account mapping defined in `reference/`.

```text
processed/
└── homologation/
    └── financial_statements/
        ├── 2021/
        ├── 2022/
        ├── 2023/
        ├── 2024/
        └── 2025/
```

The files in this zone are **not uploaded manually as source files**. They are generated by the project's Python scripts from the data stored in `interim/`.

---

## 4. Reference

`reference/` contains the reference material required for the account homologation process.

```text
reference/
└── homologacion_cuentas.xlsx
```

This file defines the account-level mapping across the different financial reporting structures present in the source data (NIIF, Formulario 101 SRI, and the additional form), and is the basis the processing scripts use to generate the homologated datasets in `processed/`.

### Rules

- Maintained manually by the team; not generated by the pipeline.
- Changes to the mapping should be reviewed before being used by the processing scripts.
- Low in volume compared to the other zones, but critical to the correctness of `processed/` and `panel/`.

---

## 5. Panel

`panel/` is reserved for the final analytical datasets produced by the pipeline.

The main expected product is the integrated financial panel for 2021–2025:

```text
panel/
└── financial_panel_2021_2025.parquet
```

This layer represents the final analytical product after integration, cleaning, validation, and the transformations required by the project.

---

## 6. Data Flow

The general pipeline is:

```text
SCVS source files
      │
      ↓
    raw/
      │
      │ extraction
      ↓
  interim/
      │
      │ Python processing + homologation ← reference/
      ↓
 processed/
      │
      │ integration + panel construction
      ↓
   panel/
```

The project therefore separates **source preservation**, **intermediate extraction**, **processing**, **homologation reference**, and **analytical output**.

---

## 7. Access and Security

The Azure Storage Account is maintained as **private infrastructure**.

Access is intended to be controlled through **Microsoft Entra ID and Azure RBAC**, using the principle of least privilege.

In this project, only the person maintaining the cloud environment interacts directly with Azure. The rest of the team works locally with Jupyter notebooks and does not need Azure credentials for day-to-day work; the maintainer is responsible for uploading source files to `raw/` and syncing outputs across the other zones.

The normal development flow (for the maintainer) is:

```text
Developer
   ↓
az login / Microsoft Entra ID
   ↓
Python + DefaultAzureCredential
   ↓
ADLS Gen2
```

Storage Account keys and connection strings should not be hard-coded in the repository.

For team members or collaborators who only need to consume an authorized dataset (e.g., the final panel), access can be granted through a read-only Azure role such as `Storage Blob Data Reader` at the appropriate scope.

## 8. Project Responsibilities

| Layer | Purpose | Main producer |
|---|---|---|
| `raw/` | Original source files | Source / manual upload |
| `interim/` | Extracted and intermediate source data | Extraction scripts |
| `processed/` | Transformed and homologated datasets | Python pipeline |
| `reference/` | Homologation mapping and supporting reference material | Manual (team-maintained) |
| `panel/` | Final analytical dataset | Python pipeline |

---

## 9. Design Principles

The Azure architecture follows these principles:

1. **Preserve the original source data.**
2. **Do not modify files in `raw/`.**
3. **Generate processed datasets through code rather than manual editing.**
4. **Keep each transformation stage separated.**
5. **Keep manually maintained reference data (e.g., homologation mappings) separate from generated outputs.**
6. **Keep the storage infrastructure private.**
7. **Use identity-based authentication instead of embedding credentials in code.**
8. **Use least-privilege access for collaborators and consumers.**
9. **Keep the Python code and pipeline logic in GitHub while storing large data files in Azure.**
